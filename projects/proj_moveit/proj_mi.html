MoveIt 2 Motion Planning for the Franka Research 3

Configuring the FR3 with MoveIt 2 using the MoveIt Setup Assistant and developing a custom C++ interface for joint-space and task-space motion planning.

Overview

This project focuses on integrating the Franka Research 3 (FR3) manipulator with MoveIt 2 for motion planning and execution in ROS 2. The MoveIt configuration was generated using the MoveIt Setup Assistant and adapted for the FR3 manipulation stack.

The generated configuration is launched using demo.launch.py, providing the MoveIt planning environment and RViz interface for visualizing and executing planned robot motions.

MoveIt Setup Assistant

The FR3 MoveIt configuration was generated using the MoveIt Setup Assistant. The FR3 robot description was loaded into the assistant and the required MoveIt configuration was created for motion planning.

The generated configuration defines the required MoveIt components for loading the FR3 model, configuring the planning group, and launching the MoveIt planning environment. The resulting configuration is maintained in the fr3_moveit_config package.

Launching MoveIt 2

After generating the MoveIt configuration, the planning environment can be launched using the provided demo.launch.py launch file. This starts the MoveIt 2 planning components and RViz, providing an interactive interface for visualizing the FR3 and testing motion planning. 

ros2 launch fr3_moveit_config demo.launch.py

Motion Planning Demonstration

With the MoveIt environment running, target poses can be specified through the MoveIt RViz interface. MoveIt generates a trajectory from the current robot state to the selected target and displays the planned motion in RViz.

The planned trajectory can then be executed to observe the corresponding robot motion in the simulation environment. The current implementation focuses on motion planning and execution without user-defined obstacles in the planning scene.

From RViz Interaction to Programmatic Control

So far, the FR3 has been controlled through the MoveIt 2 RViz interface, where target poses can be selected interactively and planned trajectories can be executed through the graphical interface. While this is useful for visualizing and validating the MoveIt setup, a practical manipulation system requires motion commands to be generated programmatically.

To achieve this, the next step was to develop a custom C++ interface using the MoveIt 2 API. This allows motion targets to be provided through ROS 2 interfaces and gives the application greater flexibility in how different types of robot motion are commanded.

MoveIt C++ API Motivation

While RViz provides an effective interface for manually testing and validating robot motion, it is not sufficient when motion needs to become part of a larger autonomous manipulation pipeline. The objective was therefore to move beyond interactive control and expose MoveIt2 planning capabilities directly to application-level code, allowing robot motions to be generated, configured, and executed programmatically.

MoveIt 2 C++ API for Motion Planning

The MoveIt 2 C++ API provides a programmatic interface to the motion-planning capabilities. Through the MoveGroupInterface, a ROS 2 application can interact with a configured planning group, define different types of motion goals, and request their execution.

For manipulator motion, the API supports several ways of specifying a goal. A target can be expressed directly as a set of joint values, as an end-effector pose, or as a Cartesian motion. The interface also provides control over planning parameters such as velocity and acceleration scaling.

Once a target is defined, the API can request a motion plan from the robot's current state. If a valid trajectory is found, the planned trajectory can then be executed on the robot.

Using the Moveit2 API

MoveIt 2 exposes its motion-planning functionality through C++ interfaces that allow an application to interact directly with the planning system. For manipulator motion, the MoveGroupInterface provides a high-level interface for working with a configured planning group and exposes the main operations required to define and execute robot motion.

The interface provides functions for accessing the robot's current state, defining different types of motion targets, configuring planning parameters, generating motion plans, and executing the resulting trajectories. This places the complete motion-planning workflow within the application rather than requiring each operation to be performed through the RViz interface.

The target-setting functions are particularly important because they allow the desired motion to be expressed in different forms. Joint-value targets describe a desired robot configuration, pose targets describe an end-effector pose, and Cartesian planning functions allow motion to be specified along a Cartesian path. Once a target has been defined, the planning functions use the available robot model and planning configuration to generate a feasible trajectory.

Integrating the API into the Motion Interface

The C++ motion interface connects the ROS 2 application to the MoveIt 2 planning pipeline through the MoveGroupInterface. The interface is initialized with the required planning group, after which the common planning parameters and robot state can be configured before a motion target is supplied. 

arm_ = std::make_shared<MoveGroupInterface>(node_, "arm_links");

arm_->setMaxAccelerationScalingFactor(1.0);
arm_->setMaxVelocityScalingFactor(1.0);

The planning request is started from the robot's current configuration so that each new command is planned from the state in which the robot actually resides. 

arm_->setStartStateToCurrentState();

With the planning interface configured, the target representation is the part that changes between the different motion commands. A joint target describes the desired configuration directly through joint values, while a pose target describes the desired position and orientation of the end-effector. Cartesian motion instead describes the desired motion as a straight line path through Cartesian space but the input remains same as pose target with waypoints.

As an example, consider the pose-target interface. The requested position and orientation are received as Cartesian values. The position can be assigned directly, while the orientation is converted from roll, pitch, and yaw into a quaternion before being provided to MoveIt 2. 

tf2::Quaternion q;
q.setRPY(roll, pitch, yaw);
q.normalize();

geometry_msgs::msg::PoseStamped target_pose;
target_pose.header.frame_id = "base_link";

target_pose.pose.position.x = x;
target_pose.pose.position.y = y;
target_pose.pose.position.z = z;

target_pose.pose.orientation.x = q.getX();
target_pose.pose.orientation.y = q.getY();
target_pose.pose.orientation.z = q.getZ();
target_pose.pose.orientation.w = q.getW();

The resulting pose is then supplied to the MoveIt planning interface as the desired end-effector target. MoveIt takes this Cartesian goal together with the current robot state and the configured planning parameters to determine a suitable motion. 

arm_->setPoseTarget(target_pose);

Once the target has been defined, the planning and execution mechanism is common to the different motion interfaces. The plan() operation requests a trajectory from MoveIt 2, and the returned result is checked before the trajectory is executed. 

MoveGroupInterface::Plan plan;

bool success =
    (arm_->plan(plan) ==
     moveit::core::MoveItErrorCode::SUCCESS);

if (success)
{
    arm_->execute(plan);
}

The same sequence is followed for the other motion interfaces, with only the representation of the target changing. This provides a common programmatic interface for commanding different types of robot motion while leaving trajectory planning and execution to MoveIt 2.

The resulting motion interfaces were then tested on the FR3 to verify joint-space, task-space, and Cartesian motion through the programmatic control pipeline.

From Motion Execution to Collision-Aware Planning

This project established the complete motion-planning pipeline for the manipulator, starting with the MoveIt 2 configuration and RViz-based validation and progressing to a C++ interface for commanding different types of motion. Joint-space and task-space targets can be provided through the interface, while MoveIt 2 handles trajectory planning and execution.

The next step is to move from target-based motion planning to environment-aware motion planning. This requires representing obstacles in the MoveIt 2 PlanningScene and incorporating collision checking into the planning process so that the generated trajectories can safely navigate around the environment.
